# Бот приёма и маршрутизации заявок

Telegram-бот, который принимает заявку у клиента и доводит её до конкретного менеджера — с дедлайном, автоматической передачей дальше и панелью управления.

---

## Задача

Заявки приходят в общий чат. Кто-то отвечает, кто-то нет; через час выясняется, что клиент ушёл к конкурентам, и виноватого нет — сообщение видели все и никто.

Нужно: заявка адресуется **одному** менеджеру, у него есть время на ответ, и если он молчит — она автоматически уходит следующему. Всё видно в панели, ничего не теряется при перезапуске.

## Решение

Клиент проходит анкету из четырёх шагов. Заявка создаётся, маршрутизатор выбирает менеджера по категории, загрузке и приоритету, и отправляет ему карточку с кнопками «Беру» и «Не могу» и видимым дедлайном.

```
Lead создана
  → routing выбирает менеджера #1
  → Assignment(attempt=1, dueAt = now + slaMinutes), Lead → ASSIGNED
  → карточка с кнопками

«Беру»      → ACCEPTED, Lead → TAKEN, карточка редактируется, клиенту уходит подтверждение
«Не могу»   → DECLINED, немедленно следующая попытка
Тишина      → EXPIRED, карточка «время вышло», attempt + 1

attempt > maxAttempts или кандидаты кончились
  → Lead → LOST, сообщение в чат эскалации
```

### Два места, где обычно делают неправильно

Всё интересное в этом проекте — здесь, и оба решения по умолчанию пишутся неверно.

**Таймер живёт в базе, а не в процессе.** Наивная реализация ставит `setTimeout` на 20 минут и теряет все висящие заявки при первом же рестарте или деплое. Здесь у назначения есть поле `dueAt`, отдельный тикер раз в 10 секунд ищет просроченные и переназначает. `setInterval` в коде ровно один — сам опрос базы; ни одного таймера на конкретную заявку нет. Процесс можно убить в любой момент, ничего не потеряется.

**Гонки разрешаются условными апдейтами.** Два менеджера жмут «Беру» одновременно. Тикер эскалирует заявку в ту же секунду, когда менеджер её принимает. Оба случая решаются на уровне базы — `updateMany` с условием на текущий статус, решение принимается по `count`:

```ts
const won = await prisma.assignment.updateMany({
  where: { id, status: 'PENDING' },          // ← условие обязательно
  data:  { status: 'ACCEPTED', resolvedAt: new Date() },
})
if (won.count === 0) {
  return ctx.answerCallbackQuery('Заявку уже взял коллега или истекло время')
}
```

Никогда «прочитал статус, проверил в коде, записал». Обе гонки закрыты интеграционными тестами на настоящем Postgres.

**Выгрузка в Sheets — через транзакционный outbox.** Задание пишется в ту же транзакцию, что и заявка, и уходит отдельным воркером с экспоненциальными ретраями. Google может лежать, отвечать по полминуты или упереться в квоты — клиент этого не почувствует.

## Запуск

```bash
cp .env.example .env      # BOT_TOKEN от @BotFather, ADMIN_PASSWORD любой
docker compose up -d && npx prisma migrate dev && npm run db:seed
npm run dev
```

Поднимутся админка на `http://localhost:3000`, бот и тикер. Сид кладёт 5 менеджеров и 200 заявок за две недели, чтобы дашборд был живым с первой секунды.

```bash
npm test          # 65 тестов, включая обе гонки и выживание эскалации после рестарта
npm run typecheck
npm run db:studio
```

Postgres из `docker-compose.yml` слушает **5433** — порт 5432 на машине разработчика обычно уже занят.

### Как убедиться, что эскалация настоящая

Поставьте `slaMinutes = 1` в `/settings`, создайте заявку, **убейте процесс** на середине минуты и поднимите обратно. Заявка всё равно уйдёт следующему менеджеру: дедлайн лежит в базе, а не в памяти.

## Настройки

## Деплой

Проект умеет жить в двух режимах, и это не костыль, а прямое следствие того, что дедлайны лежат в базе: коду всё равно, кто его будит.

| | Процессный (Railway, локально) | Serverless (Vercel) |
|---|---|---|
| Бот | long polling, `src/bot/index.ts` | вебхук, `/api/telegram/webhook` |
| Тикер | цикл раз в 10 с, `src/ticker/index.ts` | `/api/cron/tick`, дёргают снаружи |
| База | Postgres в контейнере / Railway | Neon |

Переключение режима не меняет ни одной строки в `src/core`, `src/services` и `src/bot/flow.ts` — они не знают, откуда пришёл апдейт и кто позвал тик.

### Vercel + Neon

1. База — Neon, взять **pooled** connection string в `DATABASE_URL`.
2. Миграции накатить с машины по **прямому** (непулированному) адресу: `DATABASE_URL=<direct> npx prisma migrate deploy`. Через pgbouncer `migrate` не работает — ему нужны advisory-локи.
3. Переменные в проекте Vercel: `DATABASE_URL`, `ADMIN_PASSWORD`, `BOT_TOKEN`, `CRON_SECRET`, `TELEGRAM_WEBHOOK_SECRET`, при необходимости `GOOGLE_*` и `ESCALATION_CHAT_ID`.
4. После первого деплоя направить бота на домен: `npm run webhook set https://<домен>`.
5. Завести планировщик для `/api/cron/tick` — **без него эскалация не работает**:
   - план Pro: добавить в `vercel.json` блок `"crons": [{ "path": "/api/cron/tick", "schedule": "* * * * *" }]`;
   - план Hobby: Vercel Cron там ходит раз в сутки, поэтому нужен внешний планировщик (cron-job.org и подобные) на `https://<домен>/api/cron/tick?key=$CRON_SECRET` раз в минуту.

При SLA в 20 минут минутная гранулярность незаметна: заявка уйдёт следующему менеджеру с задержкой до минуты, а не мгновенно.

Роут тика идемпотентен и защищён от параллельного вызова: переходы статусов идут условными апдейтами, outbox-задания захватываются арендой. Звать его можно как угодно часто и из нескольких мест сразу.

### Railway

Один проект и три сервиса: Postgres, `web` и `worker`. Оба приложения собираются из одного репозитория и делят `railway.json` — роль задаётся переменной:

```
SERVICE_ROLE=web      # next start
SERVICE_ROLE=worker   # бот (long polling) + тикеры
```

Стартовая команда `npm run db:deploy && npm run start:${SERVICE_ROLE:-web}` одинакова для обоих: `prisma migrate deploy` идемпотентен и берёт advisory-lock, поэтому одновременный старт двух сервисов безопасен. Остальные переменные — из `.env.example`; `DATABASE_URL` подставляется ссылкой `${{Postgres.DATABASE_URL}}`.

Бот работает на long polling, отдельный домен ему не нужен — публичный адрес есть только у `web`. Важно: polling держит ровно один процесс, поэтому локальный воркер нужно остановить перед деплоем.

Google Sheets необязателен: без кредов outbox-задания честно помечаются успешными, а остальная система работает как обычно.
